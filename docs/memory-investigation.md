# 2026-11-15 内存排查

## 运行实例证据

- 进程：PID 65883，`/Applications/BeszelBar.app`，1.0.1 (2)，运行约 10 小时。
- 用户确认 Dashboard 已关闭，仅使用菜单栏。
- `vmmap`：physical footprint 4.5GB，峰值 4.6GB；大量内存已压缩或换出，RSS 不能反映完整占用。
- 第二次 `heap`：约 2,951 万次堆分配；SwiftUI `AnyTrackedValue` 字典约 1.64GB；`Charts.MeasurableAxisLabel` 有 203,279 个。首次快照为 202,999 个，后台期间仍增加。
- 菜单对象数量远低于图表标签数量（第二次快照 NSMenuItem 为 256 个），现有证据不支持把菜单重建当作这次 4.5GB 的主要来源。

## 已确认的代码缺陷

`WindowManager` 强引用 Dashboard 窗口，并设置 `isReleasedWhenClosed = false`，却没有关闭回调来解除引用或移除 `contentView`。因此关闭窗口只是隐藏它，SwiftUI 图表树仍存在。

`SystemChartsPanel.request` 包含 `hubSnapshots.lastUpdated`；后台系统轮询更新该字段后，`.task(id: request)` 会重新加载历史数据、更新图表和时间轴。隐藏窗口因而仍有持续更新图表的路径。这与堆中大量坐标轴标签累积相符；尚未取得框架内部的完整保留链，不能断言所有累积都只有这一个原因。

## 修复与验证

- WindowManager 实现 NSWindowDelegate，关闭 Dashboard 或设置窗口时移除 contentView 并清空相应窗口引用。重新打开时创建窗口，导航模型保留。
- 后台状态变化仅更新菜单栏状态；菜单内容在 menuNeedsUpdate 时构建，避免每次轮询分配整棵菜单。
- 新增两项窗口生命周期回归测试。旧代码出现 3 个断言失败：Dashboard 视图未释放、重新打开复用关闭窗口、设置窗口视图未释放。
- 修复后两项生命周期测试及四项刷新测试全部通过（6 tests, 0 failures）。

原始采样和测试日志存于 `build/MemoryInvestigation/evidence/`（忽略目录，不提交）。

## 后续后台常驻内存优化

本轮采样的运行实例为 PID 88878。`vmmap` 显示 physical footprint 为 136.1MB、峰值 312.4MB；`heap` 中仍有 131 个菜单承载视图，其中包含 98 个容器行、12 个系统行和 12 个系统详情。这个采样来自修改前的安装版，不是新旧版本的内存对比。

新增改动：

- 菜单关闭后，在下一次主队列调度时递归解除菜单项的视图及子菜单引用，再清空菜单。这样既让 AppKit 完成点击动作分发，也让关闭的 SwiftUI 图停止观察后台快照。
- 每次准备或打开菜单时更新代次标记，防止上一次关闭时排队的清理误删刚重建的菜单。保留菜单项的动作数据供已排队的动作使用。
- API 会话禁用 URLCache，集合请求绕过本地响应缓存，避免历史响应与已解码的快照重复保留。服务销毁时关闭自身创建的会话；外部注入的会话仍由调用者管理。

验证：

- 新增四项菜单生命周期回归测试。前三项在修复前出现七个断言失败，修复后通过。
- 使用 12 台主机、98 个容器的模拟菜单，连续开关三轮；每轮 131 个承载视图的弱引用均归零，随后后台轮询不会重新创建这些视图。覆盖容器的“更多”子菜单。
- 菜单和窗口生命周期、菜单实时显示、后台刷新、AppState、API、连接回退及 SSE 协议/传输共 46 项相关测试通过。
- Release 本地临时签名构建成功。未覆盖或重启 `/Applications/BeszelBar.app`；本机无可用开发者证书。

本轮原始采样和验证日志存于 `build/BackgroundMemory/evidence/`。对象释放测试确认引用已解除，但尚未测量安装新版后的长期 physical footprint 或实际节省比例。
